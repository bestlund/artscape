### 10. Walkthrough of `first.ts`
Five parts:
1. **The frame:** `runScript` reads `bot.env`, connects, runs the steps, disconnects (2-minute safety timeout). `sdk` = eyes, `bot` = hands.
2. **Looking:** `report()` only reads position and inventory.
3. **Look → decide → act:** skip the tutorial only if on Tutorial Island. This is the core pattern; the model takes over the interesting decisions later.
4. **Acting:** `await bot.walkTo(...)` waits until done and answers `success` and `message`.
5. **Checking:** actions can fail, so check and retry.

### 11. Version 2: `bots/testbot1/chop-loop.ts` (Jacob chose option 1: chop and drop)
- Chop until the backpack is full (28 slots, 18 used by the starter kit), drop all logs, repeat for `ROUNDS` (2).
- New ideas compared to `first.ts`: settings at the top, a loop with a stop condition (`while (!isFull())`), self-correction (walk back if more than 12 tiles from the trees), giving up after 5 failures in a row (= the moment to call the model, later).
- Run 1: 17 logs (7 + 10), Woodcutting level 36, about 2 minutes.
- Run 2 (Jacob watched in-game): 20 logs, Woodcutting 36 → 46 (+12,500 XP), 0 failed chops, walked back to the trees 3 times.

### 12. What data could the bot collect?
Data the bot can actually see (checked in the SDK types): position, skills/XP, inventory, worn items, bank, nearby players/NPCs/objects/ground items, game and chat messages (with sender and tick), trade state, combat events, failed actions.

Ordered by value for the research question:
1. **Hypothesis measures:** every trade (partner, gave, received, completed or declined), every chat and private message, wealth (backpack + bank + worn, valued with market prices), memory file versions.
   - **Key insight:** cheating can only be seen by linking a *promise* in chat to what happens afterwards, so a **deal log** (who promised what to whom, delivered or not) is probably the most valuable data.
2. **Why agents behave as they do:** who meets whom (nearby players / `/playerpositions`), time use per activity, failed actions, skill progress.
3. **Model and cost (project rule):** trigger, prompt, response, tokens, cost, duration, generated code, whether it ran.
4. **Demo and believability:** everyone's positions over time (replay on the map), chat transcripts.

Practical: log events as they happen plus a snapshot every ~10 s (not the full state every tick). Chat must be collected continuously with `getNewChat()`, or old messages are lost.

### 13. Idea: an ArtScape "control room" (Jacob)
A world map where each agent is shown as a portrait/head icon walking around. Click a head to see that agent's logs, give it commands, and see its POV.

Feasibility:
- **Map with agents:** mostly exists (`/mapview` draws names and trails). Portraits are a small change to the drawing. Own designed icons are easier than rendering RuneScape chat heads.
- **Click → logs:** easy once the logger exists. The logger is the foundation.
- **Commands:** possible, but they must go *through* the agent's loop (a queue), because a second controller would kick the agent's script off. Chat can be sent in "observe" mode. Commands during experiment runs would be a confound, so log them or switch them off.
- **POV:** simple version = run that agent's client in a browser tab instead of headless (one tab per watched agent, one login per account). Fancy version = a viewer built on the engine's spectator feed (`/worldfeed`, off by default). "Thinking POV" = the agent's last snapshot, prompt and decision, from the logs.
- Suggested order: logger → control room v1 (map + logs) → commands → POV. After the logger and the first model agent; Jacob can sketch the UI meanwhile.

### 14. Idea: script items → a shared routine toolbox (Jacob)
Jacob's idea: in-game items for scripts; a bot double-clicks an item (like eating a shark) to start a routine (fishing, woodcutting, cooking …) until it turns it off; every bot has the same items and picks the right one for its task.
- The core idea (a shared toolbox of tested routines the model picks from) is **better than the original plan** of the model writing code: reliable, cheap (short answers, fewer tokens), fair (identical toolbox in both conditions), easy to log.
- The in-game item itself is a detour technically (scripts run outside the game), but useful as a **visual layer** for viewers (held item or overhead text like "Chopping wood…"). Jacob's design decision, later.
- Flow: event → model reads goal, personality, memory and situation → picks routine + settings → routine runs (code loop, no model calls) → until done or the next event.
- **Decision (Jacob): routines only for now (option 1).** Option 2, routines plus code written by the model when no routine fits, is a **future plan**: it needs to be tried a few times before it can be trusted.

### 15. Logging idea (Jacob)
Separate logs per type, combined into one log at the end:
- **Activity log:** "agent 2 started woodcutting at 14:02, stopped at 14:09 with 10 logs"
- **Location log:** "agent 2 was in area X, woodcutting spot Y" (needs named areas and spots)
- Other logs (trades, chat, model calls, snapshots …)
- Combined into one timeline that the system outputs.
